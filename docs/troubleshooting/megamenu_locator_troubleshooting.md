# Playwright Troubleshooting: Hover 메가메뉴 Locator 안정화

## 1. 문제 상황

비즈하우스 카테고리 탐색 자동화에서 `상품 제작 전체보기` 메뉴에 마우스를 올렸을 때 카테고리 메가메뉴가 정상적으로 노출되는지 검증하려고 했다.

메가메뉴 전체 영역을 Playwright Inspector의 Pick Locator로 확인했을 때 다음과 같은 Locator가 생성되었다.

```ts
locator("div")
  .filter({
    hasText:
      "찾으시는 상품이 없나요?견적서가 필요하신가요?기업 대량 주문..."
  })
  .nth(4);
```

메가메뉴 자체는 찾을 수 있었지만 Locator가 긴 텍스트와 DOM 순서에 의존하고 있었다.

---

## 2. 문제점 분석

기존 Locator는 다음과 같은 특징을 가지고 있었다.

```text
div 요소 선택
+
메가메뉴 전체 텍스트를 hasText로 사용
+
nth(4)로 특정 순서의 요소 선택
```

이 방식은 현재 화면에서는 동작할 수 있지만 다음과 같은 변경에 취약할 수 있다.

```text
- 메가메뉴 문구 변경
- 카테고리 추가 또는 삭제
- DOM 구조 변경
- 동일한 텍스트를 포함하는 요소 추가
- 요소 순서 변경
```

특히 `nth(4)`는 대상 요소의 의미가 아니라 DOM 순서를 기준으로 선택하기 때문에 구조 변경 시 다른 요소를 가리킬 가능성이 있다.

따라서 Pick Locator가 생성한 값을 그대로 사용하는 것보다 메가메뉴 노출 여부를 확인할 수 있는 더 안정적인 요소를 찾기로 했다.

---

## 3. 대체 Locator 탐색

메가메뉴 내부 요소를 확인한 결과 `기업 대량 주문` 링크는 다음 특징을 가지고 있었다.

```text
- 메가메뉴가 열렸을 때 노출됨
- 다른 화면 영역에서 사용되지 않음
- link role을 가지고 있음
- 사용자에게 의미 있는 이름으로 식별 가능
```

Playwright에서는 다음과 같이 role 기반 Locator로 찾을 수 있었다.

```ts
page.getByRole("link", { name: "기업 대량 주문🏢" });
```

---

## 4. 개선 방향

메가메뉴 컨테이너 전체를 직접 찾는 대신, 메가메뉴가 열렸을 때만 나타나는 고유 요소의 노출 여부를 확인하도록 변경했다.

```ts
await page.getByText("상품 제작 전체보기").hover();

await expect(
  page.getByRole("link", { name: "기업 대량 주문🏢" })
).toBeVisible();
```

검증 흐름은 다음과 같다.

```text
"상품 제작 전체보기" 메뉴 hover
↓
메가메뉴 노출
↓
메가메뉴 내부의 고유 링크 확인
↓
toBeVisible() PASS
```

---

## 5. 왜 메가메뉴 전체 Locator를 사용하지 않았는가

메가메뉴 전체를 직접 검증하는 것이 가장 직관적일 수 있지만, 현재 DOM에서는 테스트에 활용하기 좋은 명확한 role, name, id 등이 확인되지 않았다.

Inspector가 생성한 Locator는 다음과 같이 구현 세부사항에 대한 의존도가 높았다.

```ts
locator("div")
  .filter({ hasText: "..." })
  .nth(4);
```

반면 `기업 대량 주문` 링크는 사용자 관점에서 식별 가능한 요소이고, 메가메뉴가 표시되었을 때 확인할 수 있는 대표 요소였다.

따라서 이번 테스트에서는:

> 메가메뉴 자체의 DOM 구조를 확인하는 것보다, 메가메뉴가 정상적으로 노출되었음을 사용자에게 보이는 요소를 통해 검증한다.

는 방향을 선택했다.

---

## 6. 결과

기존에는 긴 전체 텍스트와 `nth()`에 의존하는 Locator를 사용해야 했지만, 메가메뉴 내부의 고유한 role 기반 요소를 사용하도록 변경했다.

```text
기존

div + 긴 hasText + nth()
↓
DOM 구조와 전체 문구에 의존

개선

getByRole("link", { name: "기업 대량 주문🏢" })
↓
사용자에게 의미 있는 요소로 검증
```

이를 통해 메가메뉴 노출 여부를 더 읽기 쉽고 유지보수하기 쉬운 방식으로 확인할 수 있었다.

---

## 7. 배운 점

- Playwright Inspector가 생성한 Locator를 그대로 사용하는 것이 항상 최선은 아니다.
- `nth()`에 의존하는 Locator는 DOM 순서 변경에 취약할 수 있다.
- 긴 `hasText`보다 role과 accessible name을 이용한 Locator가 의도를 설명하기 쉽다.
- 컨테이너 자체를 안정적으로 식별하기 어렵다면, 해당 UI가 노출되었을 때만 나타나는 고유 요소를 검증 대상으로 사용할 수 있다.
- Locator를 선택할 때는 현재 동작 여부뿐 아니라 UI 변경 시 유지보수성도 함께 고려해야 한다.

---

## 8. 핵심 정리

이번 문제의 핵심은 다음과 같이 정리할 수 있다.

```text
메가메뉴 전체 Pick Locator
↓
긴 hasText + nth() 생성
↓
DOM과 문구 변경에 취약하다고 판단

메가메뉴 내부 고유 요소 탐색
↓
"기업 대량 주문" link 발견
↓
getByRole() + toBeVisible()로 변경
```

> **Locator는 단순히 요소를 찾는 것보다, 왜 그 요소를 선택했는지 설명할 수 있어야 한다.**
