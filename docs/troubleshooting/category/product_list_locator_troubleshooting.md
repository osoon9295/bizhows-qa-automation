# Playwright Troubleshooting: 상품 목록 검증의 특정 상품 데이터 의존 문제

## 1. 문제 상황

비즈하우스 카테고리 탐색 자동화에서 메가메뉴의 카테고리 그룹을 선택한 뒤, 해당 카테고리의 상품 목록 페이지가 정상적으로 표시되는지 검증하려고 했다.

TC의 기대결과는 다음과 같다.

> 해당 카테고리 그룹의 상품 목록 페이지로 이동하고 해당 상품 목록이 정상 표시됨

처음에는 상품 목록이 표시되었는지 확인하기 위해 특정 상품명을 직접 검증하는 방법을 고려했다.

예:

```ts
await expect(
  page.getByText("빠른배송 엽서", { exact: true })
).toBeVisible();
```

현재 화면에서는 동작할 수 있지만, 특정 상품 하나에 의존하는 방식이 운영 서비스 자동화에 적합한지 의문이 생겼다.

---

## 2. 문제점 분석

특정 상품명을 Assertion에 사용하면 테스트가 다음과 같은 운영 데이터 변경에 영향을 받을 수 있다.

```text
- 상품 판매 종료
- 상품명 변경
- 상품 노출 순서 변경
- 카테고리 내 상품 구성 변경
- 일시적인 상품 비노출
```

이 경우 카테고리 페이지와 상품 목록 기능 자체는 정상이어도 특정 상품이 사라졌다는 이유만으로 자동화 테스트가 실패할 수 있다.

즉, 테스트의 실제 목적은:

```text
특정 상품 "빠른배송 엽서"가 존재하는가?
```

가 아니라:

```text
선택한 카테고리의 상품 목록 페이지가 정상적으로 열리고
상품 카드가 실제로 표시되는가?
```

였다.

따라서 특정 상품명과 테스트가 강하게 결합되지 않도록 Locator를 다시 설계하기로 했다.

---

## 3. 상품 카드 공통 구조 확인

상품 카드의 DOM을 확인한 결과, 상품 상세 페이지로 이동하는 링크가 공통적으로 다음 URL 패턴을 사용하고 있었다.

```text
/ko/v/option
```

따라서 상품명 대신 상품 상세 페이지로 연결되는 링크를 공통 Locator로 사용할 수 있었다.

```ts
const productCards = page.locator('a[href^="/ko/v/option"]');
```

이 Locator는 다음과 같은 의미를 가진다.

```text
<a> 요소 중
href가 "/ko/v/option"으로 시작하는 요소
```

즉, 특정 상품명이 아니라 상품 상세 페이지로 이동하는 상품 카드 링크를 대상으로 한다.

---

## 4. 새로운 문제: 이 Locator만으로 카테고리를 증명할 수 있는가?

다음 코드는 상품 카드가 최소 1개 이상 표시되는지는 확인할 수 있다.

```ts
const productCards = page.locator('a[href^="/ko/v/option"]');

await expect(productCards.first()).toBeVisible();
```

하지만 이 Locator에는 `엽서카드/티켓`이라는 카테고리 정보가 포함되어 있지 않다.

따라서 이것만으로는:

> 현재 화면이 엽서카드/티켓 카테고리의 상품 목록이다.

까지 증명하기 어렵다.

예를 들어 다른 카테고리 페이지에서도 동일한 `/ko/v/option` 링크 구조를 사용할 수 있기 때문이다.

---

## 5. 개선 방향

하나의 Locator로 모든 기대결과를 확인하려 하지 않고 검증 포인트를 두 단계로 분리했다.

### 1. 올바른 카테고리 페이지로 이동했는지 확인

실제 URL에는 다음과 같이 여러 Query Parameter가 존재했다.

```text
/ko/v/category
?mock=product_list_005
&categoryName=엽서카드/티켓
&slide=2
&from=megamenu_gnb
```

현재 TC에서 중요한 값은 카테고리 페이지 경로와 선택한 카테고리명이라고 판단했다.

```ts
await expect(page).toHaveURL((url) => {
  return (
    url.pathname === "/ko/v/category" &&
    url.searchParams.get("categoryName") === "엽서카드/티켓"
  );
});
```

`mock`, `slide` 등의 값은 현재 테스트 목적과 직접적인 관련이 없어 Assertion에서 제외했다.

### 2. 상품 카드가 실제로 표시되는지 확인

```ts
const productCards = page.locator('a[href^="/ko/v/option"]');

await expect(productCards.first()).toBeVisible();
```

검증 흐름은 다음과 같다.

```text
카테고리 그룹 선택
↓
URL에서 categoryName 확인
↓
현재 페이지가 "엽서카드/티켓" 카테고리임을 검증
↓
상품 상세 링크를 가진 상품 카드 확인
↓
상품 카드가 최소 1개 이상 표시됨
```

---

## 6. 특정 상품명을 사용하지 않은 이유

다음과 같이 특정 상품명을 사용하는 방식도 가능하다.

```ts
await expect(
  page.getByText("빠른배송 엽서", { exact: true })
).toBeVisible();
```

이 방식은 코드만 보면 어떤 상품을 확인하는지 명확하다는 장점이 있다.

하지만 A03의 테스트 목적은 특정 상품 데이터 검증이 아니라 카테고리를 이용한 상품 탐색 User Journey 검증이다.

따라서 특정 상품명이 변경되더라도 카테고리 목록 기능 자체가 정상이라면 테스트가 불필요하게 실패하지 않도록 공통 상품 카드 구조를 사용하는 방향을 선택했다.

---

## 7. 자동화 시나리오 설계 반영

기존 Then2는 다음과 같았다.

```text
Then2 :
선택한 카테고리의 상품 목록 페이지로 이동한다.
```

하지만 TC의 기대결과에는 상품 목록 표시 여부도 포함되어 있었기 때문에 다음과 같이 수정했다.

```text
Then2 :
선택한 카테고리의 상품 목록 페이지로 이동하고,
상품 카드가 1개 이상 표시된다.
```

이에 따라 코드의 Assertion도 다음 두 가지 역할로 나뉘었다.

```text
URL Assertion
→ 올바른 카테고리 페이지 이동 확인

UI Assertion
→ 상품 카드 노출 확인
```

---

## 8. 결과

초기에는 특정 상품명을 이용해 상품 목록 노출 여부를 확인하려 했지만, 운영 데이터 변경에 대한 의존도가 높다고 판단했다.

따라서 다음처럼 개선했다.

```text
기존

특정 상품명 확인
↓
운영 상품 데이터에 의존

개선

categoryName URL Assertion
+
상품 상세 링크 공통 Locator 확인
↓
카테고리 정확성과 상품 목록 노출을 각각 검증
```

이를 통해 특정 상품 데이터가 변경되더라도 카테고리 상품 목록 기능 자체가 정상이라면 테스트가 불필요하게 실패할 가능성을 줄였다.

---

## 9. 배운 점

- 운영 서비스 자동화에서는 특정 상품명이나 운영 데이터가 변경될 가능성을 고려해야 한다.
- 특정 데이터에 의존하는 Assertion은 기능이 정상이어도 테스트 실패를 발생시킬 수 있다.
- 하나의 Locator로 모든 기대결과를 증명하려 하기보다 검증 목적에 따라 Assertion을 나누는 것이 명확하다.
- URL은 현재 페이지의 상태를 확인하는 데 사용할 수 있고, UI Locator는 실제 콘텐츠 노출 여부를 확인하는 데 사용할 수 있다.
- 자동화 테스트에서는 현재 통과 여부뿐 아니라 운영 데이터 변경 시에도 의미 있는 실패만 발생하도록 설계하는 것이 중요하다.

---

## 10. 핵심 정리

이번 문제의 핵심은 다음과 같이 정리할 수 있다.

```text
특정 상품명으로 상품 목록 검증
↓
상품 변경 시 테스트 실패 가능

테스트 목적 재확인
↓
특정 상품이 아니라
"해당 카테고리 상품 목록이 표시되는가?" 확인

URL에서 categoryName 검증
+
상품 상세 링크를 가진 상품 카드 확인

결론
↓
운영 데이터 의존도를 낮추면서
TC의 기대결과를 각각의 Assertion으로 검증
```

> **운영 데이터가 바뀌어도 테스트 목적이 유지되도록 Locator와 Assertion의 책임을 분리한다.**
