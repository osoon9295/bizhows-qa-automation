# Playwright Troubleshooting: 소셜 로그인 상태 재사용과 인증 세션 만료

> **유형:** 테스트 환경·사전조건 관리  
> **대상:** 비즈하우스 장바구니 주문금액 자동화  
> **범위:** 기존 상품 옵션/병렬 실행 트러블슈팅 이후의 장바구니 작업

## 1. 문제 상황

장바구니 페이지는 로그인 상태를 전제로 사용한다. 비즈하우스에는 소셜 로그인 과정이 포함되어 있어, 주문금액 계산을 검증하는 테스트마다 로그인 UI를 통과하도록 만들면 테스트 범위가 불필요하게 넓어진다.

장바구니 테스트를 진행하면서 인증 상태가 유지되지 않을 때 페이지의 로그인 상태를 먼저 확인해야 하는 상황도 있었다.

이번 문서에는 **실제 로그인 테스트 실패 로그가 제공되지는 않았으므로**, 특정 예외 메시지를 재현한 사례로 기록하지 않고 인증 사전조건을 마련하고 점검한 과정으로 정리한다.

---

## 2. 문제점 분석

주문금액 TC의 검증 대상은 다음과 같다.

```text
장바구니 상품 선택
↓
주문금액 / 할인금액 / 배송비 / 총금액 반영
```

소셜 로그인 절차까지 매번 테스트하면 인증 제공자 화면, 로그인 정책, 추가 인증 등의 외부 조건 때문에 장바구니 테스트가 영향을 받을 수 있다.

즉, **로그인 여부는 이번 TC의 테스트 대상이 아니라 사전조건**으로 분리할 필요가 있었다.

---

## 3. 인증 상태를 저장하는 방법

Playwright가 실행한 브라우저에서 직접 로그인한 뒤 인증 상태를 파일로 저장했다.

```bash
npx playwright codegen --save-storage=playwright/.auth/user.json https://www.bizhows.com/ko
```

브라우저가 열리면 수동으로 로그인하고, 저장된 인증 상태를 이후 테스트에서 사용하도록 설정했다.

```ts
test.use({
  storageState: "playwright/.auth/user.json",
});
```

`storageState`는 로그인 관련 쿠키·스토리지 상태를 재사용하기 위한 기능이다. **로그인 세션이 영구적으로 유효하다는 보장은 없다.**

---

## 4. 저장한 상태가 만료되었을 때의 문제

`user.json`이 존재하더라도 시간이 지나면 서비스의 인증 세션이 만료될 수 있다.

따라서 장바구니 요소를 찾지 못한다고 해서 곧바로 Locator 오류라고 판단하지 않도록 했다.

```text
장바구니 요소 미탐색
↓
로그인 상태 확인
↓
인증 실패라면 storageState 갱신
↓
장바구니 시나리오 재실행
```

장바구니의 실제 기능 결함과 인증 사전조건 실패를 구분하는 것이 목적이었다.

---

## 5. 개선 방향

장바구니 테스트와 별도로 로그인 상태를 빠르게 확인하는 진단용 테스트를 사용했다.

```ts
import { test, expect } from "@playwright/test";

test.use({ storageState: "playwright/.auth/user.json" });

test("저장된 로그인 상태 확인", async ({ page }) => {
  await page.goto("https://www.bizhows.com/ko");
  await expect(page.getByRole("button", { name: /^.+님$/ })).toBeVisible();
});
```

위 예시는 실제 로그인 화면에서 관찰한 사용자 이름 버튼을 기준으로 한 **진단 방식**이다. 사용자명 표시가 변경되면 Locator를 다시 확인해야 한다.

---

## 6. 테스트 데이터와 보안 관리

저장된 인증 상태 파일은 민감할 수 있으므로 버전 관리 대상에서 제외한다.

```gitignore
playwright/.auth/
```

코드 저장소에는 다음만 남긴다.

```text
tests/auth/
  auth-check.spec.ts   # 진단용

playwright/.auth/
  user.json            # Git에서 제외
```

`auth-check.spec.ts`는 주문금액 TC를 대체하지 않으며 자동화 TC 수에도 별도로 포함하지 않았다.

---

## 7. 자동화 시나리오 설계 반영

```ts
import { test, expect } from "@playwright/test";

test.use({ storageState: "playwright/.auth/user.json" });

test("장바구니 선택 상태에 따른 주문금액 검증", async ({ page }) => {
  await page.goto("https://www.bizhows.com/ko/v/step3-cart");

  // 로그인 절차가 아닌 장바구니 선택 및 금액 계산을 검증한다.
});
```

로그인이 안 된 경우에는 금액 계산 로직을 수정하기 전에 인증 상태부터 확인한다.

---

## 8. 결과

- 소셜 로그인 UI를 자동화 코드에서 직접 반복하지 않고 인증 상태를 재사용하도록 구성했다.
- 인증이 만료되는 경우 저장 파일을 다시 생성해야 한다는 운영 조건을 확인했다.
- 로그인 상태 확인용 진단 테스트를 별도로 두어 장바구니 TC 실패와 구분할 수 있게 했다.
- **세션 지속 시간과 만료 조건은 확인되지 않았으므로** 구체적인 만료 주기를 단정하지 않는다.

---

## 9. 배운 점

- 테스트 대상과 사전조건을 분리하면 실패 원인을 좁히기 쉽다.
- `storageState`는 로그인 과정을 생략하게 해 주지만 세션 만료까지 해결하지는 않는다.
- 인증 파일은 테스트 데이터이면서 보안상 보호해야 할 파일이다.
- 진단 테스트와 실제 TC는 목적을 구분해서 관리해야 한다.

---

## 10. 핵심 정리

```text
소셜 로그인 필요
↓
테스트마다 로그인 UI 자동화?  → 장바구니 테스트에 불필요한 의존성
↓
직접 로그인 후 storageState 저장
↓
장바구니 테스트에서 인증 상태 재사용
↓
실패 시 로그인 진단 → 필요한 경우 인증 상태 갱신
```

> **장바구니 금액 검증에서는 인증을 사전조건으로 관리하고, 로그인 실패와 장바구니 기능 실패를 구분한다.**
